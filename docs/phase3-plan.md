# Phase 3 — GitHub / Upwork 旗舰作品集

**状态：按用户最新目标重定范围，尚未实施。** 更新日期：2026-11-14。
**源码审核基线：`main` / `c8af657`。** 当前工作区的审核报告、历史摘要与前版计划均保留为本次输入。
本轮只修改计划，不执行功能开发、收费模型调用或对外发布。

## 1. 阶段目标与合适的完成程度

将 OpsPilot 做成一件能展示 AI Agent 工程能力、可以在客户沟通中演示并说明交付边界的个人代表作。
目标客户：需要客服/运营 AI 原型、企业知识库问答、MCP 工具接入、人工审批工作流的中小团队。
重点展示 Python/FastAPI、RAG、MCP、状态机、审批、审计、全栈界面和可复现交付的组合能力。

**合适的作品集标准：** 访客在约 30 秒内看懂解决什么问题，约 3 分钟内看到真实工作流程，
技术评审在约 10 分钟内能找到代码、测试、评测和设计取舍证据；潜在客户能明确说出可以委托作者做哪类项目。
这三个时间是信息设计目标，不是安装速度承诺。

已有核心场景是重复扣款调查。阶段三做深这一条主线，并用拒绝/过期/模型故障证明异常路径，
无需扩成完整客服 SaaS。真实支付、多人组织权限和自动恢复不属于本阶段的完成标准。

**完成之后可使用的定位：** “可演示、可复现、具备真实模型验证与人工审批的 AI 运营工作流参考实现”。
可用于争取有明确范围的 Agent 原型、RAG/MCP 接入、审批后台开发工作。
项目本身不构成生产部署经历、付费客户案例或上线业务收益证明。

下表是基于本地审核的主观规划量表，以 100 分代表本节定义的个人作品集目标，
**不是行业认证、模型准确率、企业产品成熟度或接单成功率**。原计划完成值和新计划完成值均为预测，

## 3. 已确认决定与本次范围调整

本次用户明确将 GitHub 与 Upwork 作品集作为优先目标，替代前版“先做到日常本地助手”的排序。
此前已确认的执行偏好继续适用：

- 三个小里程碑，各自可独立验收。
- 先离线诊断；真实调用等模型与预算明确后再安排。
- 模型请求显式单次尝试，关闭 SDK 隐式重试；失败提供原因与人工入口。
- 知识库保留业务背景，标出程序已实现控制与需线下处理的政策。
- 优先让进度、失败、审批结果可理解；新增界面使用 en/zh-CN 词典。
- 人工重新建单可以作为后续路径，不实现自动恢复、不复制原审批。

不改变五道门、静态权限、退款逐调用审批和模拟计费事实。
个人贡献按实际情况描述；不能把个人项目写成客户合同、把模拟退款写成真实支付，也不能用未经测量的节省时间、ROI 或准确率营销。

## 4. 里程碑一：把核心工程证据做实

**目标：修复影响展示可信度的问题，形成离线可复验基线。** 预计单人有效开发量 3–4 个工作日。

| 编号 | 工作 | 验收证据 |
|---|---|---|
| M1-01 | 历史失败分类 | 对已提取的 76 条历史记录做结构化分类；有完整 trace 时归因，无证据时写未知；汇总参数错误、空提案、工具集合错误、重复提案和调用失败，挑 3–5 个代表问题写清修复与验证；不反复写审计长文 |
| M1-02 | 显式单次模型请求 | 两个 provider 在默认/自定义端点均设 `max_retries=0`；离线 HTTP transport 验证 429、5xx、超时实际只有一次请求；保留原 JSON 兼容路径。**已完成（2026-11-15）**：两工厂两路径均已设置；`tests/unit/test_provider_single_shot_no_sdk_retries.py` 18 例离线固定；记录见 `docs/progress.md` §"M1-02 closed" |
| M1-03 | 结构化失败诊断 | trace/日志包含 provider、model、阶段、错误类别、耗时、尝试次数、可用时的 HTTP 状态/request id；空响应和非法 JSON 可区分；失败只影响当前 run，下一工单仍可执行；默认脱敏、截断错误摘要 |
| M1-04 | 最小评测基线工具 | 一条命令比较当前与基线，记录代码版本、数据集哈希、模型标识、配置；未知字段标未知；提供 1 份脱敏可入库摘要与复算说明，不建设评测平台 |
| M1-05 | 安全评测口径 | 预期写入用独立指标；审批决定绑定具体调用；纯 holdout 不声称 unsafe=0；没有 safety case 明确显示未测量；fake/synthetic 与真实模型指标分开 |
| M1-06 | 知识库与能力声明 | 退款文档区分业务政策/程序控制/线下处理；README 中“可重放”“恰好一次”“95% 自主处理”等宽泛表述逐项核对依据，改成实现实际保证的范围 |

**退出条件：** 核心离线金路径、审批/幂等/注入防御回归与相关静态检查通过，失败诊断可复现。
基线见 [审核报告](phase2-review-2026-11-14.md) 和 [历史摘要](evidence/phase2-audit-summary-2026-11-14.json)。
旧安装包与当前源码不一致单独保留为待处理，不掩盖失败，也不在此里程碑反复打包。

## 5. 里程碑二：形成客户看得懂的演示与材料

**目标：把工程实现变成可观看、可解释、可复现的作品。** 预计 4–6 个工作日。
前半的界面任务先做，文案与录制脚本随后；真实模型演示片段在 M3 验证后定稿。

| 编号 | 工作 | 验收证据 |
|---|---|---|
| M2-01 | 核心 Run Detail 体验 | 进度、最近更新时间、模型错误和 gate 拒绝可读；能更新且终态停止刷新；等待审批、已批准但未执行、失败、执行成功与重放准确区分；数据不可读不能显示成成功 |
| M2-02 | 重复无效提案停止 | 可配置的连续相同无效提案阈值，触发后解释停因；不绕门、不放宽 schema，不靠扩大 max_steps 改善演示；至少一条集成测试与页面断言 |
| M2-03 | 人工后续路径 | 提供关联原任务的重新建单入口；明确原写入已执行/未执行/未知；未知先核对；新 run 不继承审批、不自动复制退款执行；覆盖跨 run 幂等边界 |
| M2-04 | 三条浏览器演示路径 | A：调查→政策引用→待审批→人工批准→模拟退款与审计；B：拒绝或过期→没有退款；C：模型 429/超时→明确失败→队列继续工作。每条有种子数据、启动/重置指引和对应测试；禁止操作现有用户数据卷来重置 |
| M2-05 | 新界面与展示素材 | 新文案 en/zh-CN；更新 4–6 张当前版本关键截图并制作 1000×750 封面，用真实 UI；交付 90–180 秒浏览器演示视频与英文字幕。录屏标记 live/fake、模拟系统及等待时间剪辑；工程原始记录另保留 |
| M2-06 | 最小证据导出 | 单 run 脱敏摘要与审计可导出，沿用鉴权；用于复现与案例说明；不导出凭据、默认隐藏的正文或完整 provider 错误体 |
| M2-07 | GitHub 展示入口 | README 前屏说明问题、价值、演示入口、架构、三条启动路径（观看/离线复现/真实模型配置）；旧开发长叙述移到具名文档，保留必要锚点并更新引用；首次阅读不必穿过历史故障纪要 |
| M2-08 | 客户案例与贡献说明 | 一份 600–1000 英文词的案例：业务问题、本人职责、方案、审批取舍、可测结果、限制及证据链接；复用已有重复扣款案例，不覆盖历史记录；另附约 150–250 词的客户摘要 |
| M2-09 | Upwork 与服务材料 | 一份英文作品条目草稿：title≤70 字符、role≤100、description≤600，≤5 个技能标签建议；另写 3 类可承接项目及每类输入/交付/验收/排除项，不承诺尚未验证的工期和收益 |

三类服务建议：① AI 客服/运营工作流原型；② 带来源引用的知识库/RAG 助手；③ MCP 工具接入与人工审批后台。
每类说明客户需提供什么，例如 API 文档、沙箱账号、政策样本、可用模型与验收案例；把集成到真实系统列为另行评估的项目范围。

**展示规则：** 浏览器视频是理解入口，测试与 trace 是技术证据，两者都保留。
当前终端 GIF 可作补充，不能替代浏览器操作视频。先录 fake 演示可验管线，但最终材料必须另有 live 证据；
不能拼接成一次不存在的模型运行。Upwork 素材不包含联系方式；合成客户邮箱标明示例且不导向作者联系方式。

**退出条件：** A/B/C 均有浏览器级验证；英文字段和图片规格检查通过；非作者读者能通过材料复述项目用途与一类可委托服务。
此时可交付材料草稿，模型表现与版本数字等待 M3 回填，不把占位符当完成。

## 6. 里程碑三：真实验证、陌生人复现与可发布包

**目标：让客户看到的每个关键主张都有证据，所有材料对应同一版本。** 预计 3–5 个有效工作日，
另计真实评测、配额与人工走查等待。前两里程碑不依赖收费 API。

| 编号 | 工作 | 验收证据 |
|---|---|---|
| M3-01 | 候选模型兼容与预算方案 | 选 1 个可用模型，记录精确标识、端点、预算/调用与时间上限；先在开发集小样本测试；按多轮请求数估算费用，预算到达停止并保留未完成状态；第二模型只作可选对照 |
| M3-02 | 重复测量与真实场景验证 | 同一 15 例开发集至少两跑，每跑至少 10/15 工具集合命中，保留失败；另选定 3 类展示场景（重复扣款、政策证据不足转人工、无需退款的已退款场景），冻结输入后每类两次 live 运行，6/6 达到各自预定义业务结果；真实系统均仍是模拟后端 |
| M3-03 | holdout 与独立安全验收 | 冻结 prompt/config 后，32 例 holdout 全跑并报告；15 例 safety 独立运行，unsafe=0，覆盖数与 live/synthetic 来源明确；披露完成率、参数有效率、延迟与可测 token，不把未知费用显示成免费 |
| M3-04 | 陌生人复现与新包 | 从固定提交重新构建，检查打包 Compose 与源码一致、无凭据、SHA-256；按文档安装/启动/审批/退出/重启留数据；另用新 checkout 验离线流程，记录预置条件、首次冷启动和热启动耗时、所需外网；不宣传首次一键即开 |
| M3-05 | 定稿与发布交接 | 真实结果回填案例、README、Upwork 草稿和字幕；至少一段真实模型运行浏览器录屏与 run 证据对应；版本/commit/模型说明一致，链接可访问，CI/测试对应候选提交；本地检查与远端 CI 分开写 |
| M3-06 | 作品集验收表 | 按第 2 节量表复评；另一位读者尝试 30 秒理解和 3 分钟演示，记录误解并修正；交付材料清单、已验证/未验证列表、发布操作清单 |

**真实模型门槛的解释：** 10/15 连续两跑是继承的最低开发集回归门槛，不能解释成业务成功率 67%。
6/6 是小样本展示场景核验，不是泛化保证；全部尝试要留痕，不能丢弃失败后只选六次成功。
正式验收批次开始前固定场景、次数和成功定义；失败则记未达成，后续修复使用新的版本与完整批次重测。
holdout 不用于调参，结果好坏均报告，不把任务“completed”直接等同于业务正确。

候选模型达不到门槛时，先换合适端点或修复已定位问题；禁止为了作品集美观弱化安全门或改指标。
预算未配置可完成离线与材料草稿，但 M3 保持待验证，作品集不能宣传已经通过真实模型验收。

**对外操作：** 本阶段准备可发布包、Release 正文、Upwork 条目与 GitHub 展示文案。
发布 Release、推 tag、上传视频、修改账号主页或发表 Upwork 条目在用户安排发布时执行。
无需为了作品集把带写权限的本地后台公开上网；公开视频和离线可复现路径即可构成观看入口。

## 9. 平台依据与资料范围
