## 5. 失败归因（按 [eval-failure-classification-2026-11-15.md](eval-failure-classification-2026-11-15.md) 的类别）

1. **空提案（检索弃答）3 例 × 2 跑：harness 确定性策略，非模型故障。** tool-005/006/012 两跑均 0 工具调用、`escalated=true`、恰好 2 次模型调用。已用 runner 同款检索栈直接验证：三例 ticket 的检索最高分分别为 0.171 / 0.172 / 0.215，均低于 `RETRIEVAL_MIN_SCORE=0.22`，run 走 `RETRIEVING → RESPONDING` 弃答升级，规划轮从未运行。对照组 tool-001 的检索最高分 0.372（不弃答）。这与历史分类报告 §5.4 的结论完全一致；该 3 例的 `expected_tools` 非空，故指标计为 miss——**即使模型完美，这 3 例也不可能在当前检索阈值下命中**，即两跑实际"可竞争"的 case 上限为 12/15。
2. **工具集合错误（多提/少提）：模型侧主因。** 除去弃答 3 例，其余 12 例两跑全部集合不等。典型形态：
   - **少提**：tool-001 两跑均未提 `crm.get_customer`（run2 甚至未提 `billing.issue_refund`）；tool-002 两跑均以 `issues.create` 替代 `billing.get_invoice`。
   - **多提**：tool-003/004 大量混入 `knowledge.search`、`issues.search`、`issues.create`；tool-007 提了 `crm.get_account` 与 `billing.list_transactions`。
   - **重复**：tool-001 run1 对 `billing.list_transactions` 重复 4 次；两跑合计多余调用 16 次。
3. **参数遵从不是瓶颈。** argument validity 两跑均 1.000——B2 修复（工具目录+参数 schema 进提示词）的效果保持，所有提出的调用都通过 gate-1。
4. **无病态循环失控。** 单 case 最多 86/15≈6 次模型调用（run1），无 case 触发 `max_steps=24` 上限，无 StructuredOutputError。与 MiniMax 时代"19 次调用产出 16 行工具记录"的病态形态相比，DeepSeek V4.1-Flash 的循环行为显著更健康，但工具集合选择仍不达标。

**综合归因：与方案 §1 对 MiniMax 的判断同构——剩余差距是模型对"该选哪些工具"的判断力。** 在 12 个可竞争 case 中，DeepSeek V4.1-Flash 两跑命中 3 与 2，远低于 10/15；且 8/15 的 run 间一致率说明这不是单次噪声。按方案 §4.1 S2 的规则，S2 未通过，不进入 S3/S4 冻结验收。

## 6. 端点与预算说明

- **网关性质**：`127.0.0.1:3425` 是本机 magpie 桌面应用的本地 API 网关，上游为用户已有的第三方订阅（Cursor Free 等）路由，**按订阅计费、不产生按 token 的 API 账单**。本次两跑未消耗可计费额度，实测费用 $0；$25/模型预算上限未被触碰。
- **路由选择过程**（如实记录）：`sensenova-token-plan/deepseek-flash` 首测正常，但正式跑首例即遇上游 429（"Cursor: usage limit reached / Model unavailable on Free"），判定不可靠弃用；`workbuddy/deepseek-v4.1-flash` 压测稳定（连续 12/8/4 连发零失败），选为正式路由。三次启动失败（429×2、json_schema 信封不被网关约束导致 0 例可测×1）均为**调试记录，不计入正式两跑**；正式两跑在最终冻结配置下完整重跑。
- **json_object 降级的依据**：该网关对 `json_schema` 严格信封返回 200 但不约束输出（content 为自由文本），`reasoning_content` 中亦无合规 JSON；启用仓库原生 `OPENAI_JSON_OBJECT_FALLBACK=true` 后返回合规 JSON。该降级路径即方案 §2.4 为 MiniMax 时代验证过的同一路径。
- **展示场景 6/6**：预算允许但 S2 未达标，按方案 §4.1 的顺序约束，展示场景的模型验收以 S2 通过为前提，故本次未执行，留给 S2 达标后（或换模型后）的后续批次。
