# Phase 4 — UI 优化、文档收尾与版本冻结

**状态：执行计划已确定，尚未开始实施。**  
**目标：** 在第三阶段现有功能上完成最后一轮 UI 打磨、交互收尾、发布材料整理和版本冻结。阶段四结束后，项目默认进入维护冻结；只有真实用户采用并产生明确需求时才重新立项。

## 1. UI 选型结论

### 主 UI 库：HeroUI

本次从 `E:\ui-libraries\web\` 的候选库中选择 **HeroUI** 作为 Web UI 主库，版本基线使用本地参考集的 HeroUI 3.2.7，真正安装版本以实施时锁定的 npm lockfile 为准。

选择原因：

- 当前项目已经是 Next.js 16、React 19、Tailwind CSS 4，HeroUI 的本地说明明确覆盖 React 19、Next.js 和 Tailwind 4，迁移阻力最低。
- HeroUI 建立在 React Aria 交互基础上，适合键盘、焦点、弹层、菜单、选择器、对话框和无障碍行为。
- 默认视觉比当前裸 Tailwind 组件更完整，适合做“直观、现代、可演示”的审批后台。
- 组件带有过渡、状态和主题能力，能够改善审批卡、运行状态、Toast、Drawer、Dialog、Tabs 和表格筛选的反馈。
- 当前组件仍由项目自己控制，业务逻辑、API 数据和安全边界不会交给 UI 库。

配套使用：

- **Tailwind CSS**：继续作为布局和局部样式基础，不做全量替换。
- **Lucide**：仅用于统一线性图标；图标必须有可见文字或 aria-label，不用图标代替关键文案。
- **现有 i18n**：继续使用 `en` 和 `zh-CN`，新增文案必须进入词典。
- **CSS motion**：优先使用 HeroUI/Tailwind 的状态过渡；只为反馈和层级服务，不制作循环装饰动画。

### 候选排除

| 候选 | 结论 | 原因 |
|---|---|---|
| shadcn/ui | 不作为主库 | 可定制性很强，但组件源码和交互组合需要自行维护；适合从零建立设计系统，本项目收尾阶段成本偏高 |
| Radix Primitives / Themes | 不作为主库 | 行为和无障碍优秀，但视觉与动效仍需较多自定义 |
| Mantine | 不作为主库 | 完整度高，但会引入另一套主题、样式和组件心智模型，与当前 Tailwind 结构重复 |
| Ant Design | 不作为主库 | 后台能力强，但默认企业视觉较重，迁移和覆盖成本大，容易让界面失去独特性 |
| Material UI | 不作为主库 | 生态成熟，但 Material 视觉与当前 OpsPilot 的审计/审批风格不完全一致 |
| Primer / Carbon | 作为规则参考 | 用于间距、信息密度、颜色语义和设计审查，不直接替换组件 |
| HeroUI | **采用** | 视觉完成度、交互特效、React 19/Next/Tailwind 4 兼容性最符合本阶段 |

**不采用“全站重写”。** 先做一个垂直切片：Dashboard → Run Detail → Approval action。只有垂直切片通过视觉、可访问性、数据一致性和回归测试后，才推广到其余页面。

## 1.1 已确认的交互决策

2026-11-16 通过四轮选择确认：

| 项目 | 已确认方案 |
|---|---|
| 视觉方向 | 审计工作台：克制、清晰、专业，突出状态与风险 |
| 动效 | 只用于状态变化、展开、加载和操作反馈 |
| 改造顺序 | 先 Dashboard、Run Detail、Approvals，再统一其他页面 |
| 主题 | 浅色为主，补齐所有核心页面的深色细节 |
| 导航 | 保留顶部导航，增加当前页高亮和清晰操作入口 |
| Dashboard | 待审批与失败任务并列为两个主卡片，下面显示最近运行 |
| Run Detail | 默认显示关键步骤，完整时间线可展开 |
| 审批 | 右侧固定审批卡集中显示风险、金额和决定按钮；窄屏移到主内容顶部 |
| 风险色彩 | 琥珀=等待/需人工，红色=失败或危险，绿色=完成 |
| 卡片 | 细边框、轻微阴影、低圆角 |
| 文案 | 直接说明事实和下一步，不使用模糊的产品化措辞 |

| 图标 | 统一使用 Lucide 线性图标，同时保留文字标签 |
| 冻结 | 功能回归、视觉截图、可访问性、安装包和 README 全部指向同一 release commit |

## 2. 现状判断

现有 UI 已经能完整表达核心流程，但视觉上偏“功能验证版”：

- Dashboard 信息准确，但主次层级弱，状态卡、列表、知识索引缺少统一视觉重点。
- Run Detail 信息完整，但时间线很长，审批区和证据区的注意力竞争明显。
- 审批状态已经有颜色语义，但按钮、风险提示、执行结果之间的层级还可以更直接。
- 当前界面以静态边框和文字为主，加载、刷新、成功、失败、过期和展开/收起的反馈不足。
- 页面截图适合证明功能存在，尚未达到“客户打开就能理解产品”的展示完成度。
- 现有功能、权限、审批门、审计和 API 契约是收尾阶段的固定边界，UI 优化不能改变它们。

## 3. 阶段四的交付原则

1. **事实优先。** UI 不能把“已批准”显示成“已执行”，不能把读取失败显示成零，也不能用动画掩盖未知状态。
2. **一个页面一个主动作。** Dashboard 的主动作是查看需要处理的任务；Run Detail 的主动作是理解状态；Approval 的主动作是核对后决定。
3. **渐进披露。** 首屏给结论，详情按需展开；完整 trace、工具参数和原始结果仍可查。
4. **动效服务于状态。** 只用于页面进入、状态变化、展开/收起、Toast、按钮反馈和等待提示；禁止循环动画、自动轮播和无意义弹跳。
5. **保留操作可达性。** 键盘、焦点、Esc 关闭、屏幕阅读器标签、减少动态效果设置必须可用。
6. **真实双语。** 所有新增用户可见文案进入 en/zh-CN；机器状态码、工具名和审计字段保持原值。
7. **不扩展产品边界。** 不引入新工单类型、多人 RBAC、真实支付、自动恢复、多模型路由或后台大重构。

## 4. 执行里程碑

### F4-A — 设计基线与依赖落地

**目标：** 在写组件前固定视觉语言和安全边界。

任务：

- 建立 `docs/ui-selection-2026-11-16.md`，记录 HeroUI 选型、版本、许可证、替代方案和回滚方式。
- 安装并锁定 `@heroui/react`；优先采用 Table、Modal、Toast、Tooltip 等完整交互组件，同时只打包实际页面用到的代码并检查 bundle 变化。
- 建立 OpsPilot 语义 token：背景、表面、边框、正文、次要文字、成功、等待、危险、焦点、审批强调色。
- 固定容器宽度、间距节奏、字号层级、圆角、阴影和响应式断点。
- 保留现有 `StatusBadge`、`Pill`、`Panel`、`ErrorPanel` 的数据语义，先重构其视觉实现。
- 为 motion-reduce、深色模式、焦点环和键盘导航写基础规则。
- 记录 HeroUI 和现有 Tailwind 之间的样式优先级，避免全局 CSS 随意覆盖组件状态。

验收：

- `npm run lint`、`npm run typecheck`、`npm run check:types` 通过。
- 依赖 lockfile 可重复安装；没有把 HeroUI 源码仓库复制进 OpsPilot。
- 一张 token/组件状态表覆盖默认、hover、focus、pressed、disabled、loading、success、warning、danger。
- 未改变 API、权限、状态机和数据库结构。

### F4-B — 垂直切片：Dashboard → Run Detail → Approval

**目标：** 先完成最重要的一条操作路径。

Dashboard：

- 将“待审批”和“失败任务”设为首屏两个视觉焦点。
- 状态卡增加明确的语义图标、数字、说明和入口按钮。
- Recent runs 改为可扫读列表：状态、工单、更新时间、需要的动作。
- 空状态、加载状态、API 错误状态使用明确的 HeroUI Alert/Spinner/Empty pattern。
- 不用纯颜色传达状态；每个状态有文字和图标辅助。

Run Detail：

- 将顶部改为“当前结论区”：状态、最后更新时间、下一步、是否需要人工。
- Timeline 默认展示关键节点，完整步骤可展开；保留步骤序号、原始时间和 API 事实。
- Sources、Approval、Customer reply、Tool calls 采用 Tabs 或折叠区，避免首屏过长。
- 审批卡突出确定性风险说明、模型理由和 Approve/Reject 的区别。
- 对“批准但尚未执行”“执行失败”“重放”使用不同结果视图。
- 刷新/轮询状态可见，终态停止刷新。

Approval：

- 审批列表突出金额、工具、客户/工单、风险说明、创建时间、过期时间。
- 决策操作使用确认 Dialog；Dialog 中显示确定性风险摘要、工具参数和当前状态。
- 重复点击、过期和已决定状态使用结构化反馈，不显示成功假象。
- 关键按钮在键盘和窄屏布局下仍可用。

验收：

- 桌面和窄屏各走一遍 golden path。
- 使用 fake provider 覆盖待审批、批准完成、拒绝、过期、失败和空数据。
- 浏览器测试断言 UI 文案与 API/数据库事实一致。
- 原有审批 API、幂等和安全测试全部保持通过。

### F4-C — 其余页面与交互收尾

**目标：** 让整个 dashboard 使用同一套视觉和行为语言。

范围：

- Tickets：表单分组、字段说明、提交中/失败/成功反馈、重复外部 ID 提示。
- Runs：状态筛选、分页、空结果、失败入口、可读的更新时间。
- Knowledge：索引状态、重建按钮、进度反馈、失败后重试提示。
- Locale switcher：改为可识别的 Select/Segmented control，保留首屏无闪烁。
- ErrorPanel：使用统一 Alert，但保留 API code、status 和原始机器信息。
- Toast：仅用于已发生的动作，例如“索引完成”“审批已记录”；不能用 Toast 表示仍在进行的任务。
- Skeleton：只用于已知结构的短暂加载，不能把异常状态伪装成加载。

验收：

- 每个页面都有 loading / empty / error / success / disabled / keyboard focus 状态。
- en/zh-CN 字典保持 parity；新增文案不直接写入组件。
- 页面无横向溢出；键盘可完成表单提交、筛选、展开、审批和关闭弹窗。
- `prefers-reduced-motion` 下无关键内容丢失。

### F4-D — 视觉 QA、可访问性与性能

**目标：** 把“好看”变成可以检查的交付标准。

检查项：

- 视觉层级：每页一个主焦点，标题、状态、动作和证据顺序清楚。
- 信息密度：Run Detail 默认不把所有原始 payload 挤在首屏；重要内容可在 3 秒内定位。
- 颜色对比度：正文、状态、链接、焦点和按钮满足可读要求。
- 交互反馈：按钮按下、异步等待、成功、失败、过期和不可用状态都有反馈。
- 响应式：至少验证 1280px、1024px、768px 和 390px 宽度。
- 性能：首屏不引入不必要的大型客户端包；HeroUI 组件按页面使用情况导入；长 timeline 不一次性制造过多 DOM。
- 视觉回归：更新关键页面截图，保留 before/after 对比，截图来自同一 fixture 和同一 viewport。
- 可访问性：Playwright/axe 或等价检查覆盖 landmark、label、button name、dialog、focus order 和 status announcement。

验收：

- 新增 UI e2e 与现有 58 项纯逻辑检查均通过。
- 关键页面截图通过人工审查；差异必须能解释。
- 无严重可访问性问题；任何暂留问题进入冻结报告。
- bundle 和构建时间变化有记录，不能以“看起来更好”掩盖性能退化。

**目标：** 交付一个可展示、可安装、可复验的最终版本，然后停止常规更新。

- 重新构建 web、desktop 和 installer；验证打包 Compose 与源码一致。
- 重新走安装、启动、索引、工单、审批、模拟退款、重复审批、错误状态、退出和重启保留数据。
- 更新 README 首屏截图、UI 说明、运行指引和限制说明。
- 生成 UI 变更说明：采用了什么、哪些页面改变、哪些功能明确没有改变。
- 保存最终视觉截图、演示视频或录屏，以及一份最终验收表。
- 记录已验证、未验证、已知限制和后续仅在真实采用时才重开的条件。

最终验收：

- Python、web、desktop 相关检查通过。
- 核心浏览器 golden path 通过；无旧安装产物混入。
- 新包 hash、版本、截图、视频、README 和测试结果全部指向同一 commit。

## 5. 推荐的视觉方向

OpsPilot 不做通用 SaaS 的彩色卡片墙，采用“审计工作台”方向：

- 主色：中性石墨/深蓝，强调色只用于当前需要处理的审批动作。
- 成功：低饱和绿色；等待：琥珀；失败：红色；信息：蓝色。
- 背景和表面有轻微层级，边框比阴影更主要。
- 字体保持系统 sans；工具名、ID、状态码和 JSON 使用等宽字体。
- 高风险动作使用明确文本、金额和后果，不靠红色按钮制造紧张。
- 动效时长短、方向一致；页面状态变化比装饰更重要。
- 保持中英文文本长度变化下的布局稳定。

## 6. 变更优先级

P0：

- HeroUI 依赖和 token 基线。
- Dashboard、Run Detail、Approval 垂直切片。
- 状态、审批、错误和异步反馈准确。
- 键盘/焦点/窄屏不阻塞核心任务。

P1：

- Tickets、Runs、Knowledge、Locale switcher 统一收尾。
- 视觉回归截图、性能和可访问性检查。
- README、安装包、最终验收记录。

P2：

- 细微阴影、图标微调、空状态插图、非关键过渡。
- 全量桌面 shell 的装饰性视觉更新。

若工期不足，优先保留 P0 和冻结证据，删减 P2 装饰，不删安全、可访问性、数据真实性和安装验证。

## 7. 不做什么

- 不在阶段四更换后端架构、模型路由、数据库、MCP 协议或审批语义。
- 不把 UI 动效做成自动化执行暗示。
- 不实现真实支付、多人审批、完整 RBAC、多租户或公网 SaaS。
- 不在未验证的情况下增加“AI 准确率”“节省成本”“生产就绪”等宣传数字。
- 不为了截图伪造模型结果、审批结果、退款结果或用户反馈。
- 不把 HeroUI 源码仓库复制进项目；组件按页面实际使用引入，避免无意义的包体增长。
- 不在冻结后继续做“顺手优化”；新需求进入真实采用后的新阶段。

## 8. 计划规模

建议 7–10 个单人有效开发日，另加：

- 依赖安装与构建排障：0.5–1 天。
- 浏览器回归和截图审查：1–2 天。
- 新安装包与冷机走查：0.5–1 天。

阶段四不是功能扩展阶段，而是“视觉一致性 + 交互可信度 + 最终证据 + 版本冻结”阶段。
